# AI-Assisted Design Policy (Provider-Neutral)

> **Owns:** what a design target is and where it lives, artifact boundaries,
> generated-design integration, and visual verification. **Applies to:** every
> human and AI agent working on BoGa. **Load when:** a task creates or materially changes UI.

## Policy

1. Figma and Claude Design are both valid design environments. Neither has
   automatic precedence, and a workflow may use either or both.
2. **A design target is a build input, not a spec.** It states what a build
   sets out to make; the design is expected to change while the feature is
   built, and those changes never flow back into the target. After the build,
   the shipped app, its code and tests, and the specs and facts below are the
   truth; the target is history.
3. Before implementing a significant UI task, identify its design target. A
   significant task creates or materially changes a screen, reusable
   component, layout, interaction, or user-visible state. The target may be
   Figma frames, Claude Design artifacts, a declared mixed set, or a
   repo-native brief plus reference screenshots. When sources are mixed,
   state which source governs each screen or state.
4. **The target lives with the work, never in the specs.** Record it beside
   the UX Contract (`docs/specs/08-ux-delivery-standard.md`): in the task card
   or the PR body, with links to the external artifacts, which stay in their
   native environment (do not mirror a Figma file or Claude Design workspace
   into the repository). A repo-native brief too long for a PR body goes in
   `docs/plans/**`, deleted with its plan. Reference and comparison
   screenshots stay in the gitignored `apps/mobile/artifacts/` tree and are
   linked as evidence. Nothing goes under `docs/specs/**`; `docs-check` fails
   on any file in the retired target directory, `docs/specs/ui/design-targets/`. <!-- docs-check: historical-path -->
5. The repository is authoritative for production behavior, React Native code,
   accessibility, UI tokens, tests, and runtime assets. A target guides a
   change; it does not bypass the existing architecture or silently redefine
   repository contracts.
6. Code generated by any design tool is prototype material until it has been
   reviewed and integrated into the Expo Router structure, existing feature
   components, and `apps/mobile/components/ui/` tokens and primitives, with
   accessibility and tests added or updated as required.
7. Complete UI work by rendering every relevant state in the running app,
   capturing a new screenshot at the target device or viewport, and comparing
   it with the target. The PR records each material deviation and its reason;
   the target is not edited to match. Visual review supplements, and never
   replaces, the required `./boga` gates and accessibility/behavior checks.
8. If design artifacts, target screenshots, requirements, repository docs, or
   current code conflict during the build, report the sources and impact in
   the task or PR. Do not silently choose by tool, timestamp, or convenience.

## What outlives the build

When the build ships, move anything that must last to its one owner, in the
same PR:

| What the build settled | Owner |
| --- | --- |
| A product decision a user can observe (what counts, what is shown, the words) | a fact in `docs/product/` (the product owner approves) |
| A rule shared by several screens | `ux-rules.md` or `design-language.md` |
| A screen's layout and behaviour | the component's header comment and its Jest tests; `screen-map.md` for route entry, exit and states |
| Everything else (pixels, spacing, mock copy, how the design evolved) | nowhere: the shipped app is the record |

## Commit boundaries

Commit reviewed, integrated production code and intentional runtime assets.
Do not commit:

- design targets, target records or reference screenshots outside
  `docs/plans/**`;
- complete Figma dumps or exports of an entire design workspace;
- entire AI conversations;
- parallel generated implementations beside the integrated React Native path.
