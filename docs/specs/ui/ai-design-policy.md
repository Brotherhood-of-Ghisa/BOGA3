# AI-Assisted Design Policy (Provider-Neutral)

> **Owns:** design-source acceptance, artifact boundaries, generated-design
> integration, and visual verification. **Applies to:** every human and AI agent
> working on BoGa. **Load when:** a task creates or materially changes UI.

## Policy

1. Figma and Claude Design are both valid design environments. Neither has
   automatic precedence, and a workflow may use either or both.
2. Before implementing a significant UI task, identify its accepted design
   target. A significant task creates or materially changes a screen, reusable
   component, layout, interaction, or user-visible state. The target may be
   Figma frames, Claude Design artifacts, a declared mixed set, or a repo-native
   brief plus reference screenshots. When sources are mixed, state which source
   governs each screen or state.
3. External design artifacts stay in their native environment. Do not mirror a
   complete Figma file or Claude Design workspace into the repository.
4. The repository is authoritative for production behavior, React Native code,
   accessibility, UI tokens, tests, and runtime assets. An accepted design
   target guides a change; it does not bypass the existing architecture or
   silently redefine repository contracts.
5. Code generated by any design tool is prototype material until it has been
   reviewed and integrated into the Expo Router structure, existing feature
   components, and `apps/mobile/components/ui/` tokens and primitives, with
   accessibility and tests added or updated as required.
6. Complete UI work by rendering every relevant accepted state in the running
   app, capturing a new screenshot at the target device or viewport, and
   comparing it with the accepted target. Record material differences and
   intentional deviations; visual review supplements, and never replaces, the
   required `./boga` gates and accessibility/behavior checks.
7. If design artifacts, target screenshots, requirements, repository docs, or
   current code conflict, report the sources and impact in the task or PR. Do
   not silently choose by tool, timestamp, or convenience. Resolve material
   conflicts explicitly before changing the accepted target or production
   contract.

## Pinning an accepted target

Keep the target record small and reviewable:

- `Target`: stable native link(s), including the frame/artifact and revision or
  date when available.
- `Brief`: the intended hierarchy, interaction, and constraints in a few
  bullets.
- `States`: the selected target screenshots and their device/viewport and UI
  state.

The record may live in the task or PR. When the target must remain durable in
the repository, store a concise record under `docs/specs/ui/design-targets/`
and commit only the selected, accepted target screenshots needed to disambiguate
it. Runtime comparison captures normally remain in the gitignored
`apps/mobile/artifacts/maestro/` tree and are linked as task/PR evidence.

## Commit boundaries

Commit reviewed, integrated production code; intentional runtime assets; and,
when needed, a concise target record with selected accepted screenshots. Do not
commit:

- complete Figma dumps or exports of an entire design workspace;
- entire AI conversations;
- placeholder or speculative screenshots;
- parallel generated implementations beside the integrated React Native path.
